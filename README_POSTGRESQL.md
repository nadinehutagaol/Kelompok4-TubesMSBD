
# PostgreSQL + Multi-Database Setup (Trrrible)

This implementation preserves the original Laravel application features, imports the original MySQL data into PostgreSQL, and adds a separate PostgreSQL analytics database and a digital-product Marketplace.

## Database layout

The project uses two separate PostgreSQL 16 databases hosted by the same Docker service:

- `trrrible` — the primary application database. It contains the original application schema and imported data, Laravel-related tables, and the Marketplace tables and database components.
- `trrrible_analytics` — the reporting database. It contains `designer_metrics`, `daily_metrics`, `analytics_refresh_logs`, and `marketplace_product_metrics`, together with analytics views.

Laravel has two database connections:

- `pgsql` connects to the primary `trrrible` database.
- `analytics` connects to `trrrible_analytics`.

The databases are separate PostgreSQL databases even though they run in the same Docker container.

## First-time setup

### Prerequisites

- Docker Desktop
- PHP and Composer
- Node.js and npm
- The project source code

### 1. Configure the environment

Copy `.env.example` to `.env`, then configure the local PostgreSQL connection:

```env
DB_CONNECTION=pgsql
DB_HOST=127.0.0.1
DB_PORT=5437
DB_DATABASE=trrrible
DB_USERNAME=postgres
DB_PASSWORD=postgres

ANALYTICS_DB_HOST=127.0.0.1
ANALYTICS_DB_PORT=5437
ANALYTICS_DB_DATABASE=trrrible_analytics
ANALYTICS_DB_USERNAME=postgres
ANALYTICS_DB_PASSWORD=postgres
```

The Docker Compose configuration maps host port `5437` to PostgreSQL's container port `5432`. If you change the database password, keep `DB_PASSWORD` consistent with the Docker Compose environment.

### 2. Start PostgreSQL

From the Laravel project root, run:

```bash
docker compose up -d
docker compose ps
```

Wait until the `postgres` service reports that it is healthy.

On the first startup with an empty Docker data volume, the initialization script creates and prepares both databases. It loads the primary schema and source data, configures sequences, installs the primary database components, creates `trrrible_analytics`, and loads its initial schema.

**Important:** Docker's PostgreSQL initialization scripts run only when the database data directory is first initialized. Changing an initialization script later does not automatically rerun it against an existing Docker volume.

### 3. Install PHP dependencies and generate the application key

```bash
composer install
php artisan key:generate
```

### 4. Install the Marketplace database extension

The Marketplace migration is applied to the primary database:

```bash
php artisan migrate --path=database/migrations/2026_11_19_000001_create_marketplace_tables.php
```

Then install the Marketplace analytics table and view in the analytics database:

```bash
MSYS_NO_PATHCONV=1 docker compose exec postgres psql -U postgres -d trrrible_analytics -f /postgresql/marketplace_analytics.sql
```

The migration and SQL script are intended to be applied once to a database that does not yet contain the Marketplace extension. Do not rerun them blindly against a database where the extension is already installed.

Create the public storage link used for product preview images:

```bash
php artisan storage:link
```

### 5. Refresh analytics

```bash
php artisan analytics:refresh
```

Run this command after significant changes to primary application data or before viewing refreshed analytics reports.

### 6. Install frontend dependencies and start the application

```bash
npm install
npm run build
php artisan serve
```

Open `http://127.0.0.1:8000`.

> Do not run `php artisan migrate:fresh`, `php artisan migrate:refresh`, or `php artisan db:wipe` on the imported database. These commands can delete the imported application data.

## Database components implemented

In addition to primary keys, unique constraints, foreign keys, checks, and indexes, the primary database includes:

1. `trg_audit_like_insert` trigger.
2. `trg_audit_comment_insert` trigger.
3. `fn_audit_social_activity()` trigger function.
4. `fn_shot_engagement(bigint)` stored function.
5. `sp_cleanup_expired_sessions()` stored procedure.
6. `view_content_engagement` view.
7. `view_top_designers` reporting view.
8. `trg_marketplace_payment_audit` payment audit trigger.
9. `fn_log_marketplace_payment()` payment audit trigger function.
10. `fn_product_sales_total(bigint)` stored function.
11. `view_marketplace_sales_summary` Marketplace sales view.

The analytics database includes the `daily_metrics`, `designer_metrics`, `analytics_refresh_logs`, and `marketplace_product_metrics` tables, indexes, `view_analytics_overview`, and `view_marketplace_analytics_overview`.

The social audit triggers record newly inserted likes and comments in `activity_audits`. Historical rows are imported before the triggers are created, so the import does not fabricate audit history. The payment audit trigger records payment creation and status changes in `marketplace_audit_logs`.

The `sp_cleanup_expired_sessions()` procedure is a manual database procedure; it is not run automatically by the application.

## Multi-database and Eloquent ORM

- Existing application Eloquent models use the default `pgsql` connection for the primary `trrrible` database.
- `App\Models\Analytics\DailyMetric` and `App\Models\Analytics\DesignerMetric` explicitly use the `analytics` connection.
- The analytics refresh command aggregates data from the primary database into the separate analytics database.
- The admin report reads analytics data after refresh and can fall back to the primary-database reporting view if analytics has not yet been refreshed.

Example model configuration:

```php
protected $connection = 'analytics';
```

This allows Laravel Eloquent ORM to query the analytics database through the separately configured connection.

## Backup and restore

Back up each database from the PostgreSQL container:

```bash
MSYS_NO_PATHCONV=1 docker compose exec postgres pg_dump -U postgres -d trrrible -F c -f /tmp/trrrible_backup.dump
MSYS_NO_PATHCONV=1 docker compose exec postgres pg_dump -U postgres -d trrrible_analytics -F c -f /tmp/trrrible_analytics_backup.dump
```

Copy the backup files from the container to the project directory:

```bash
docker compose cp postgres:/tmp/trrrible_backup.dump ./trrrible_backup.dump
docker compose cp postgres:/tmp/trrrible_analytics_backup.dump ./trrrible_analytics_backup.dump
```

Restore into an existing, empty target database (create the target database first):

```bash
MSYS_NO_PATHCONV=1 docker compose exec -T postgres pg_restore -U postgres -d TARGET_DATABASE --no-owner < trrrible_backup.dump
```

For the analytics backup, use `trrrible_analytics_backup.dump` and the analytics target database name.

Backup and restore were tested for both databases. The primary restore contained 25 tables and 8 Marketplace products. The analytics restore contained 4 tables, including 10 daily metric rows, 103 designer metric rows, 8 Marketplace product metric rows, and 4 refresh-log rows at the time of the test.

The `*.dump` rule in the root `.gitignore` excludes local database backup files from Git. Keep backup files in a safe location outside source control.

## Resetting the local Docker database

Only if you intentionally want to delete the local PostgreSQL volume and rebuild from the bundled source data:

```bash
docker compose down -v
docker compose up -d
```

**Warning:** `docker compose down -v` permanently deletes the PostgreSQL data stored in this project's Docker volume. Do not run it if you have data you need to keep.

## Marketplace extension (digital products)

The Marketplace extends the original application while preserving its Shots, designer profiles, social interactions, and Get Hired features.

### Marketplace capabilities

- Designers can publish digital products with a public preview and a private downloadable file.
- Visitors can browse and search products and filter by category or price.
- Authenticated users can manage a cart, check out using an academic payment simulation, and view purchase history.
- A buyer can download a digital file only when the order is marked paid and belongs to that buyer.
- Sellers can review their published products and recorded sales totals.

### Marketplace routes

- `/marketplace` — public catalog.
- `/marketplace/products/{slug}` — product detail.
- `/marketplace/sell` — publish a digital product (login required).
- `/marketplace/cart` — shopping cart (login required).
- `/marketplace/orders` — buyer order history (login required).
- `/marketplace/my-products` — seller product list and sales summary (login required).

### Transaction and inventory behavior

Checkout uses Laravel `DB::transaction()` with row-level `lockForUpdate()` on cart items and products. Stock deduction, order creation, order-item snapshots, simulated payment creation, and cart cleanup occur in one database transaction. If validation or a database write fails, the transaction is rolled back. The payment simulation does not charge real money. Private digital files are served through an authenticated order-ownership and paid-status check.

The `trg_marketplace_payment_audit` trigger writes payment events to `marketplace_audit_logs`. `view_marketplace_sales_summary` provides product-level paid sales, and `fn_product_sales_total(bigint)` returns the paid gross sales for one product. The analytics database receives refreshed product aggregates in `marketplace_product_metrics` and exposes `view_marketplace_analytics_overview`.

### Concurrency test

A parallel checkout test was performed with two users requesting 4 units each of the same product while only 5 units were available.

- User 107's checkout succeeded for 4 units.
- User 108's checkout was rejected because the remaining stock was insufficient.
- The final stock was 1 unit.
- The product `sales_count` increased from 10 to 14.
- The order count increased from 4 to 5.
- The payment count increased from 4 to 5.
- The rejected user's cart retained its 4 requested units.

These results are consistent with the expected behavior of the transaction and row-level locking logic: the stock did not become negative, and only one order and payment were created in this test.

## Other database tests performed

- **Transaction rollback:** a test update was deliberately followed by an exception; the transaction rolled back and the product's original stock value remained unchanged.
- **Analytics ORM access:** Eloquent successfully read 10 rows from `DailyMetric` and 103 rows from `DesignerMetric`; the Marketplace product model read 8 products from the primary database.
- **Backup and restore:** both PostgreSQL databases were backed up and restored into separate test databases, and their tables and sample row counts were checked.
- **Analytics refresh:** `php artisan analytics:refresh` completed successfully and populated the designer, daily, and Marketplace product analytics data.

These statements describe tests performed on the development database at the time of verification. Results can change when the database is modified.

- Do not run destructive migration or Docker volume reset commands unless the team intentionally wants to rebuild the local database.
- Apply the Marketplace migration and analytics SQL only once to a database that does not already contain the Marketplace extension.
